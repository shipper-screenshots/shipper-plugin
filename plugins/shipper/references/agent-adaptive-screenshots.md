# Agent Adaptive Screenshots

Owner: Agent Shipping / Adaptive Screenshots. Orchestrated by Create Screenshot Set; Creative Lab remains the creative authority. Read this reference for generic screenshot creation needing a format, explicit device/spec/orientation requests, adding formats, multi-spec requests, or platform-dependent scope. Ordinary edits to a suitable destination use existing edit primitives without Adaptive.

The [decision tables](agent-adaptive-screenshots-policy.json) are packaged reasoning policy, exercised by repository fixtures. They neither call tools nor parse user language, folders or screenshots. Facts must come from user intent and current native observations. No table can grant authority. Technical fields and constraints belong to the generated [MCP contract](mcp-mutation-contract.json) and [types](mcp-mutation-contract.d.ts), checked against the live contract through [Core Authority](core-authority.md). Missing capability means STOP and characterize it; never emulate Adaptive with lower-level mutations.

## Resolve scope after preparation

Continue only after [prepare-shipper](../skills/prepare-shipper/SKILL.md) supplies the exact workable project/session. Preserve its accepted ambiguity and creation rules. Creating a project still uses its native default primary, even when the requested output is iPad or Mac. Do not create/populate unrequested formats to manufacture an adaptation source. Native adaptation always derives from the primary, not a recently edited non-primary variant.

Read `list_screenshot_specs`. Resolve all requested destinations against its editable records before any Adaptive WRITE. Priority: **explicit user scope → relevant verified Target evidence → native defaults**. Never infer IDs, dimensions, orientation support or defaults from model memory or response order.

| Intent / evidence | Resolution |
| --- | --- |
| Explicit supported destinations | Those observed native records; no Target prerequisite |
| No explicit format or usable verified context | `defaults.global` |
| Verified evidence establishes iOS | `defaults.devices.iPhone` |
| Verified evidence establishes macOS | `defaults.devices.mac` |
| Verified evidence establishes both | Both native device defaults |
| iPad without orientation | The only observed editable iPad record; verify uniqueness |
| Mac without size | `defaults.devices.mac` |
| Supported orientation variant | Match the source device/size and requested orientation to native discovery |

Current native discovery exposes eight editable specs, including Dynamic Island Medium Portrait and Landscape. The native global and iPhone defaults currently resolve to `iPhoneDynamicIslandMediumPortrait`; consume the returned defaults rather than fixing these values in Plugin policy. New-project defaults do not convert existing projects or replace an explicitly requested legacy format. For an existing Face ID Large portrait set (`iPhone65Portrait`), “add iPad and a landscape version” means the observed iPad portrait destination and matching `iPhone65Landscape`, not Medium Landscape or iPad landscape. Unsupported explicit iPad Landscape, Dynamic Island Large Landscape or Mac Portrait must not silently become another format. Explain the limitation; clarify only if the intended device/orientation is genuinely ambiguous.

Target is optional and informs scope without restricting design. Explicit Mac wins even when Target exposes iOS only; no ASC permission, refresh or bind is needed for that design request. A currently verified, relevant observation can be consumed without another Target flow. Invoke the unchanged [Target policy](target-app.md) only for genuinely ASC-dependent intent such as “all platforms available for my app.” Preserve its ambiguity, security and Keychain boundaries. One selected iOS version proves only that positive context; it does not prove Mac unavailable or establish exhaustive platform support. If additional platform evidence is insufficient, use safely established/default scope and disclose the limit rather than inventing platforms or claiming “all.” The historical Screenshot Specs gap in Target's consumer notes is superseded by this Adaptive capability; this does not change any Target discovery/binding rule or the still-separate Primary Metadata gap.

## One destination at a time

Resolve the destination list first, then execute it **sequentially**. One destination is one Adaptive atomic operation across its existing locale lists. The entire multi-spec workflow is not a transaction. If a later destination fails, keep successful earlier destinations and report the exact incomplete portion; never roll them back.

Before each destination, use the exact `inspect_project` form with prepared project/session and requested native spec. Consume both destination and primary inventories completely: follow the snapshot-bound cursor, concatenate locale fragments in returned order and retain empty lists. A partial page cannot authorize WRITE. On stale continuation, discard the partial observation and restart from canonical current state; if repeated concurrent/session changes prevent a sound observation, stop dependent work.

- `exists = true`: preserve the destination, including sources, mockups and independent edits. **Do not call adapt_screenshot_spec again**, even if inactive, empty or visually imperfect. An empty existing locale with `canvases = []` is valid, not absence or a repair request. Separate explicit redesign/edit intent uses normal supported Creative/edit primitives with fresh scope; Adaptive is not a repair or selection workaround.
- `exists = false`: use the complete fresh `snapshotRef` and expected project revision with `adapt_screenshot_spec`. Empty primary lists may create a valid empty destination retaining the locales. Never fabricate a Canvas ID, presume one blank Canvas, or expect a mockup without a Canvas. Creative Lab can subsequently create/design in the newly active destination using existing creation primitives and fresh canonical observations.

Preserve exact-count and meaningful-work protections from [Creation Decisions](../skills/create-screenshot-set/references/creation-decisions.md). `create_canvas` and structural operations retain their current active-list boundary; scoped edits do not imply scoped creation. If a separate edit brief needs unsupported inactive-list structure, stop that dependent action and characterize the capability gap; do not switch by replaying Adaptive or emulate a new transaction.

On confirmed success consume the returned IDs, revision domains, current state and commit generation. Complete any result pagination before inventory-dependent follow-up. Scoped operations use the observed scoped revision; the active Canvas ledger is a different domain. Never invent revisions. Sources/edits have their own atomic units and guards.

## Sources and native mockups

Discover source candidates before adaptation where relevant, assign only after committed destination IDs exist. Use the authorized catalog and lazy previews to establish app, device family, physical mockup/source context, capture orientation, locale and meaningful story correspondence. Capture orientation is evidence about the screen content, not a requirement to match the outer Canvas orientation. Folder/collection names and returned relative hierarchy (including App / Device / Locale conventions), metadata and image content are semantic evidence only. Opaque `folderRef` and `authorizedSourceRef` remain authority. No rigid folder parser, filename-position matching, filesystem authority or automatic source-matching engine. `01.png` on two devices does not establish equivalence. Preview more or ask the minimum clarification when evidence remains ambiguous.

For each **new** destination Canvas, Core supplies no inherited screenshot pixels and a visible native-resolved empty mockup. Assign a compatible source through `set_screenshot_source` with exact `scope {locale, specification}` and fresh scoped revision when evidence supports it. Compatibility follows the destination device family and physical mockup/source context; it is not `source orientation == Screenshot Spec orientation`. Existing same-device captures remain candidates when only the outer Canvas orientation changes. In particular, a portrait iPhone capture inside a portrait physical iPhone mockup on an `iPhone65Landscape` Canvas is valid. Do not require separate landscape app captures, reject or clear an otherwise compatible source merely because the Canvas is landscape, or rotate capture pixels to match the Canvas. Same family alone is not sufficient: ground the app, screen content, locale and physical source compatibility in native metadata, catalog evidence and previews. The table's `sourceCompatibility` decision records this grounded judgment; only its compatible-candidate outcome supplies `compatibleEvidence=true` to `source`, and fresh opaque source authority is still required for assignment.

Cross-device safety is unchanged: iPhone captures are not automatic fallbacks for iPad or Mac mockups. Those destinations need compatible device-specific captures. No compatible source, incompatible source, stale ref or refused assignment leaves the valid destination and visible empty mockup intact; report source pending. Never force phone captures into tablet/Mac, fabricate app screenshots, rotate portrait pixels to fake landscape, or hide the mockup to mask missing pixels. Existing destinations are not automatically cleaned or resourced.

Use scoped `list_mockups` when a definition choice is actually needed. Native results own compatibility and resolution; no Plugin mapping or bezel constants. The current portrait catalog includes iPhone 18 Pro Black, iPhone 18 Pro Silver, iPhone 18 Pro Glacier and iPhone 18 Pro Burgundy; select a color only from the exact live scoped result, and preserve an existing selection unless the user or the creative brief calls for a change. The current iPhone 18 Pro catalog has portrait resources only, and native landscape discovery falls back to the portrait iPhone 17 definition; do not promise iPhone 18 Pro as a landscape choice. Canvas orientation is not physical device orientation. Real Device's native renderer chooses the flat bezel at zero X/Y and its 3D view when X/Y is tilted; the Plugin supplies only supported rotation properties and verifies the rendered result. Do not invent a 3D mode or force a 90° rotation.

Keep four concepts separate: Screenshot Spec defines the outer Canvas/export format; the mockup represents the physical device; the app capture supplies that device's screen content; mockup Rotation is an independent creative transform. Never infer Rotation from a spec name, Canvas dimensions or an orientation label. Landscape alone must not cause a rotation mutation or imply Rotation = 90°. Preserve the native physical orientation by default: for the native iPhone 17 Black portrait mockup in UC3, Rotation remains 0 unless Creative Lab independently grounds a different rotation or tilt in composition/design judgment. Use the `rotation` decision separately from scope and source compatibility. Creative rotation remains allowed; it does not establish capture compatibility or authorize rotating capture pixels.

For “Also create a landscape version of these screenshots” on an existing iPhone 6.5 Portrait set, resolve the observed `iPhone65Landscape` record, adapt the absent destination once, keep the same Creative Target and native physical iPhone, consider the existing compatible iPhone captures, and assign fresh authorized sources with exact scope. For the five-Canvas UC3 set, preview all five, recompose for the wider Canvas, and verify saved-generation coverage. Do not leave otherwise compatible portrait iPhone captures unassigned merely for lack of landscape-specific captures. Existing destinations still follow the preservation rule above; this example is not permission to rerun Adaptive on the already-created failed UC3 destination.

## Creative Target and Localization

For add-spec work, preserve the accepted Creative Target; do not generate an unrelated concept. For fresh creation, follow the existing concept/source/Target decision before Canvas mutations, including direct-Shipper fallback when generation is unavailable. One requested multi-spec set shares the same Target; format changes do not reset generation or refinement budgets.

Native Adaptive is an editable structural baseline, not a finished visual result. Preview **every destination Canvas**, including all retained locale lists, with exact scope and current revisions. Review hierarchy, whitespace, typography, readability, mockup size/position, device/source correctness, balance, clipping and composition. An empty list has no Canvas to preview; report its state honestly.

Refine material weaknesses through existing edit primitives, then preview again and perform final ordered review within the existing two substantive passes. Preserve the Target's visual system and relationships, not exact coordinates: iPad may need repositioning/scaling, Mac a different composition, landscape a landscape-aware layout. Do not merely resize or rotate. An explicitly requested format permits the compositional changes necessary for that format under the existing explicit-user-instruction boundary; it does not permit unrelated Art Direction or discard the Target's material graphic families. For a default-resolved format, realize the same visual design in that format and retain the existing four-reason fidelity boundary. See [Image Generation Orchestration](../skills/create-screenshot-set/references/image-generation-orchestration.md). Creative Lab owns judgment; Core/MCP gain no creative engine.

Adaptive is **FREE**, with no PRO/Localization/Shipping admission. Structurally preserving English/French/Korean lists is not translation and does not invoke `apply_localization`. Explicit translation/localization is a separate request handled by the unchanged [Localization Skill](../skills/localize-app-store-content/SKILL.md). Subsequent secondary-locale source/refinement guards remain authoritative. On entitlement refusal preserve the structural Adaptive result and report refinement pending; never bypass the guard or relabel Adaptive as PRO.

## Unknown outcome and truthful completion

`mutation_outcome_unknown` → never blindly replay. Read fresh exact destination `inspect_project`, not `inspect_localization`, and consume every page. If canonical destination now exists completely, consume current state without inferring historical `created` or `selectionChanged`. Existing empty lists count as a complete valid destination. If absent, only a new intentional request still required by the brief may use a fresh complete observation. Concurrent change, incomplete evidence or session uncertainty stops dependent work. snapshotRef is neither a durable receipt nor an idempotency key.

Applied != Saved. After adaptation and final refinements, observe native persistence for the relevant latest commit and same persistence session. Claim saved only when native saved generation covers that commit; a newer dirty generation does not erase proof that an earlier commit was saved. Do not rerun Adaptive because saving is pending, failed or requires user action.

Report each requested destination truthfully: preserved existing; structurally created; source pending; creative refinement pending; applied/save pending; save failed/user action required; or complete and saved. Completion requires the requested scope/count, compatible source or disclosed source gap, final pixel review/refinement and native persistence evidence. A visible empty mockup can be a valid structural result without being a finished screenshot set. Successful earlier destinations survive later failure. Repository fixtures are not installed acceptance or PM UC1–UC4 visual acceptance.
