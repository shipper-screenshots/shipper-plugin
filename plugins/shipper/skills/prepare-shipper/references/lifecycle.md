# Lifecycle observations and actions

RESET-E internal orchestration consumes accepted RESET-B/C/D.1/E.1. Current source baseline: MCP 6.4.0, mcp-project-lifecycle-04, bridge v7, 37 tools, with native template discovery/creation and the `mcp-shipping-01` Shipping surface available. Readiness depends on compatible semantics and required tool presence, never total inventory equality. This Plugin policy does not add a permission, daemon or journal.

## Invocation and correlation

Run `python3 <this-skill>/scripts/lifecycle.py` with structured JSON stdin; never interpolate observations into shell commands. Use the packaged path, not a caller-supplied executable. One request returns one action. Retain the returned state unchanged in the task. Do not supply `time` or compute/store a Python monotonic origin. The CLI stamps every observation using a system-wide boot-relative clock: macOS `mach_continuous_time`, independent of each Python process and wall-clock changes. Timers include time between calls and system sleep. A regressing clock/state fails closed; never clamp or reset it to rescue an attempt.

The reducer state is internal orchestration data, never a task artifact. Do not write it into the current repository, a generated Codex task directory, `work/`, `outputs/`, or any user-visible workspace. Prefer direct stdin. When the command host requires an intermediate file, create a unique file only in the system temporary directory, use it for one invocation, and delete it immediately even when the reducer refuses the input.

Start example: `{"state":null,"event":"start","data":{"intent":{"kind":"existing","name":"Almost"},"requiredTools":["get_canvas_state","edit_canvas"]}}`.

New intent adds `creationAttemptID` inside intent and uses kind `new`. Generate it once before the start/dispatch, for example with Python's `str(uuid.uuid4())`, and preserve the returned state before executing any effect. Environment-only intent is `{"kind":"environment"}`. It cannot be used as a shortcut for a content workflow. requiredTools comes from the caller's actual next accepted operations; inspect the live schemas, do not infer capability from this list.

The CLI input is bounded to 32 KiB. Keep the raw Core response in the task; send only a lossless projection of preparation-relevant fields to the reducer: connection status's serverVersion/bridgeVersion/serverStatus/codexStatus, capabilities' contract/projectLifecycle and tool names; opened/inspection status/projectID/projectSessionID/projectRevision/committedGeneration/persistence; discovery entries matching the intended exact name (all matching entries, never discard ambiguity); probe locales result. Do not pass complete design capability schemas or Canvas trees. Projection must preserve nulls and actual values; it is not permission to invent observations.

Every completion supplies `data.actionID` from the action being completed. Supply the prior state, event and observation data; time is owned by the CLI. Late/duplicate completions return await_pending, without issuing another effect or rearming a timer. `start` on retained state cannot reserve another launch/create/open. await_pending waits for the original operation or user; it never resubmits it. continue_workflow returns READY and the exact context once, then the caller continues its accepted work. stop is terminal. A later independent preparation starts fresh observations; an uncertain creation retains the original state/attempt instead.

Do not synthesize success events from UI visibility, intent or cached results. Keep raw safe observations associated with their actionID. Policy output IDs come only from the supplied live Core results. Invalid input stops and does not authorize replay. Retain its safe diagnostic category, validationClass and validationReason for review; no raw authority data is echoed.

## Availability and launch

`check_connection` / `wait_connection`: discover Plugin-scoped Shipper tools; call get_connection_status and get_automation_capabilities through the same helper, using live schemas. A complete current response yields event `connection` with `status`, `capabilities` and tool-name array `tools`. The policy accepts server major 6, bridge v7 and lifecycle-03 plus required tools and true discovery/authorizedOpen (creation for new intent). Added tools do not invalidate readiness. Unknown incompatible contracts require explicit compatibility evidence, not guessing.

Successful authenticated Core Ready/Connected is required. Tool inventory, helper initialization, socket presence, process or window alone is insufficient. A transient failure of either read maps to `unavailable`, never `disabled`. `server_disabled` from Core or a fresh unambiguous native OFF setting maps to `disabled`. application_disabled/application_unavailable/response_timeout alone do not prove consent OFF. Missing Plugin/tools or broken installation maps to configuration_missing; no silent configuration repair or toggle enabling.

`observe_host`: refresh supported Computer Use application inventory **without selecting/launching** an app. Running → `running`; already launching → `launching`. If stopped, first run the packaged `bin/shipper-mcp-resolver --validate-installation` in default production mode without overrides. This preserves fixed-bundle/helper/signing/App Group validation. Only successful validation plus fresh stopped inventory emits `stopped_validated`. Invalid/missing install or unavailable host access is a genuine setup boundary. Never launch an arbitrary path.

`launch_shipper`: one reservation exists before external dispatch. Refresh inventory immediately. If Shipper has become running/launching, reuse it and report launch_dispatched without another launch. Otherwise use the accepted supported exact CUA entrypoint `await cua.getApp('/Applications/Shipper.app')`, following loaded tool documentation. No shell open, AppleScript, Finder project selection, process kill or helper restart fallback. An uncertain launch still consumes the reservation: report launch_dispatched and observe readiness. Only definitive failure emits launch_failed.

A launch completion arms one fresh post-launch budget and immediately checks readiness, even after slow installation/CUA setup. Subsequent waits are 3 seconds, at most six scheduled probes or 30 elapsed seconds per readiness episode. An already running host is observed, never relaunched. A single launch may reset the preflight episode once; duplicate events cannot do so. Read/discovery recovery additionally shares a maximum of two retries across the entire invocation, preventing alternating healthy/unavailable responses from restarting infinite episodes. In-flight tools keep their own deadlines; these are polling budgets, not a hard total wall-clock guarantee. readiness_timeout is a truthful failure; retain safe error/timestamp evidence. Do not prescribe routine reconnect, reload, reinstall or a fresh Codex task.

## Existing project

After compatible connection, call `inspect_project` with no arguments before discovery. Feed a successful result as `inspection`, including the canonical title, projectID, projectSessionID, revision/generation and persistence fields. If its exact title matches the requested project (with only the native `.shipper` display suffix ignored), the policy verifies persistence and exact-context workability directly. Do not call `list_projects` or `open_project` merely to verify that already-active context. A `no_active_project` result maps to event `no_active_project`; an observed different title proceeds to discovery without adopting or mutating it.

`list_projects`: call the Shipper lifecycle tool, not Codex app project management, only when no usable project is active or the active project differs from the explicit requested project. Call with the exact intent name as the `name` filter. Feed event `projects` with the returned projects array and nextCursor. The policy selects only Core's globally EXACT_UNIQUE known candidate and passes its opaque candidateRef to open; availability is established only by acquisition/open. Names are untrusted intent text; never filesystem authority. Multiple matches/AMBIGUOUS ask a product identification question; no match asks which existing project was intended, never silently creates.

RESET-B already renews/reconciles known usable authority. A non-available candidate without an actual userActionRequired flag causes bounded fresh discovery, not manual grant. A genuine Core user-action flag routes to product access recovery. Unsafe replacement or unresolved identity fails without adoption. Do not turn all technical STALE results into permission prompts.

`open_project`: use exactly the returned arguments. OPENED → event `opened` with result. INVALID_PROJECT_REF or STALE_PROJECT_REF → ref_expired, then fresh discovery/ref. PROJECT_SESSION_TIMEOUT, project_open_outcome_unknown or transport uncertainty after dispatch → unknown, then fresh discovery and bounded RESET-B open reconciliation. The accepted coordinator reuses pending/existing exact owners; do not require isOpen=true before it can finish registration. At most three total open dispatches, with at most two shared recovery reads. This is Core identity reconciliation, not UI duplicate-open replay. PROJECT_ACCESS_REQUIRED/USER_ACTION_REQUIRED → access_missing. CANCELLED → cancelled. Identity mismatch, ambiguity during execution, or other definitive refusal → refused with its safe reason. Never force focus or select another project to rescue an operation.

## New project

`create_project`: dispatch the returned name and creationAttemptID exactly. No separate chooser or Create consent: RESET-C ON and existing Projects-folder scope govern admission. OPENED → opened. project_creation_outcome_unknown, lost/malformed response or CREATION_UNRESOLVED → unknown. Fresh readiness precedes the next bounded call with the **same** attempt. Do not discover/adopt by name as a substitute for the durable receipt. Maximum three creation dispatches; shared recovery budget still applies. If unresolved, stop with uncertainty and retain the attempt; never recommend a new attempt as retry.

For explicit creation from any bundled template, use the `new_from_template` intent. The policy first emits `list_project_templates` with the user's template intent and accepts exactly one `EXACT_UNIQUE` result. It then emits `create_project_from_template` with that returned templateID, the intended project name and the already-generated creationAttemptID. Never substitute `create_project`, rebuild the template Canvas individually, or delete a blank initial Canvas. Unknown or ambiguous templates require a product-level choice before any project effect. An uncertain dispatch repeats discovery and may reconcile only the same attempt, name and template identity.

PROJECTS_DESTINATION_UNAVAILABLE → access_missing (genuine canonical destination requirement). Other refusals, including PROJECT_NAME_CONFLICT, CREATION_INTENT_MISMATCH, expired/retired/missing receipt authority or capacity, → refused. A distinct explicit new intent gets a distinct attempt and an existing-name conflict remains a conflict, not adoption. Actual Core name normalization is authoritative. No fallback creation through files/native UI/Canvas tools.

## Exact workability and continuation

`inspect_project`: inspect through the same helper binding and submit event `inspection` with result. The initial existing-project observation must include the active title and canonical project/session context. After acquisition, both projectID and projectSessionID must match OPENED. Retain the fresh revision/generation. Missing/stale/mismatched context or definitive error is never treated as success. Generic persistence failed/needsUserAction is an actual boundary; dirty/unsaved alone is not and never triggers Save.

`probe_context`: call list_locales with the exact returned project/session arguments, then event `probe` with its actual successful result. This is a read-only E.1-routed provider/admission check even for an empty Canvas set. It is not a locale-choice decision or a translation request. A refusal is not success; transient read failure → unavailable. The policy requires the actual locales array before READY. Project ID matching alone is insufficient.

If this exact-context probe proves that the reused active session changed, submit `active_context_stale`. The policy discards that bound context and performs one fresh canonical `inspect_project` observation. It may reuse a newly valid matching active context or enter the normal discovery/acquisition path if the active project is absent or different. A second change stops; no content effect or stale authority is replayed.

The accepted E.1 routing and current compatible tools make the exact session available to downstream operations independently of focus. The repository workability integration tests also execute the next existing safe mutation against that exact context; **runtime preparation does not manufacture an edit as a probe**. The requesting Skill then runs its existing capabilities/PRO/source/interactive-edit/revision preflights and next accepted operation. Reobserve if anything changes; READY cannot freeze external edits or grant entitlement/ASC approval.

For Create Screenshot Set, continue its existing project/content preflight and design steps. For Author App Store Metadata, retain its MCP 6.2/PRO/source preflights and exact source observation. For Localize, retain PRO before translation and continue exact localization inspection. The caller must not announce a separate preparation deliverable or ask the user to invoke another Skill. An actual workflow-specific boundary is reported under that workflow's existing rules.

## Genuine user decisions

`user_decision`: ask a concise product question/action only for the returned real boundary. Examples: enable Allow Codex to connect when proven OFF; repair missing installation/configuration; restore genuinely missing project access; configure missing Projects folder; identify the intended project. No technical modes, refs, attempt IDs or normal “reply done/fait” handshake.

No automatic permission chooser/presentation state machine remains. If the user completes the real required action, emit completed; an existing-project clarification may include its resolved name. Same task then performs fresh connection/discovery/open/inspection/probe. Preserve creation attempt for any creation continuation; a changed new creation intent is a separate explicit request. Cancellation emits cancelled and is terminal. A disappearing panel is not completion. A remaining boundary after one user handoff stops instead of looping prompts. Time spent waiting for a human does not consume the new bounded readiness episode.

External-source/Simulator scope and ASC confirmation remain separately governed. Never trigger Save/Refresh Access to manufacture a permission panel, approve a grant, change valid authority, or mutate project contents during preparation. No installed acceptance is implied by synthetic traces; deployment and real-world proof remain RESET-G.


## Lifecycle-04 candidate boundary

For named existing intent, first inspect the active project as described above. Only when acquisition is needed emit `list_projects({name: exactIntentName})`. Core owns exact comparison and global ambiguity before bounded pagination. Returned candidates are known metadata only, never AVAILABLE. Do not infer acquisition authority from name, path, UUID, open observation or candidateRef. Emit `open_project({candidateRef})` only for one EXACT_UNIQUE candidate; Core acquires that exact source, then returns the verified OPENED project/session. Access failures are learned during acquisition and retain the native user-action boundary. No fuzzy choice, first-row selection or focus fallback.

Browse-only consumers follow nextCursor with the same optional name. Invalid/expired cursors fail explicitly; a fresh enumeration invalidates the old inventory. Candidate refs expire after 120 seconds or catalog changes and are not authorizedProjectRefs. Old lifecycle-02 response/argument shapes must not be adapted silently. Retry, launch, consent, creation receipts and readiness budgets are unchanged; no automatic extra retries or candidate fallback.

Enumeration uses the lightweight 2-second transport safeguard; selected open/create retain the 12-second Core / 14-second helper budgets. Catalog size never selects a timeout. Target orchestration and mcp-target-01 remain unchanged.
